    Architecture¶

    The service is one FastAPI application, web_service.main:app, that runs in one process. It authenticates each caller with Globus, then acts for that caller with its own AWS key: it manages the caller's IAM user, keeps the caller's records in three DynamoDB tables, and creates, deletes and reads topics on one Amazon MSK cluster.

    The request path¶

    1. A client sends an HTTPS request to the public endpoint of the Lightsail container service. Lightsail forwards it over HTTP to port 8000 of the one container, which deployment.yml names flask (Deployment).
    2. In the container, gunicorn runs one Uvicorn worker, which serves the FastAPI application. web_service/main.py builds the application and its routes in the class DiasporaService.
    3. The route handler checks the caller's token with Globus (Authentication).
    4. The handler calls the service classes in web_service/services.py:
      • WebService runs each user, key and topic operation across the classes below.
      • IAMService creates and deletes IAM users, their policies and their access keys.
      • NamespaceService checks namespace and topic names and keeps the namespace and topic records, through DynamoDBService.
      • DynamoDBService reads and writes the three tables.
      • KafkaService creates and deletes topics with a Kafka admin client.
    5. The consumer routes, under /api/v2/consumers, call ConsumerService in web_service/consumer_service.py, which keeps Kafka consumers in memory (State in memory).

    Calls to Globus, IAM, DynamoDB and Kafka block, so the handlers run them in threads. On the event loop, they would stall every other request. Produce bodies are parsed one at a time and sent at most 8 at once, and consumer fetches poll at most 3 at once, each with a limit of its own, since they hold the most memory. Every other blocking call shares a pool of 40 threads.

    The service reaches AWS with the key in AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY. Its Kafka clients connect to the brokers in DEFAULT_SERVERS over SASL_SSL with the OAUTHBEARER mechanism, using tokens that aws-msk-iam-sasl-signer-python signs with that key for the region in AWS_ACCOUNT_REGION. The service does not use the users' IAM keys for its own calls.

    Authentication¶

    Every API route takes two headers: subject, the caller's Globus identity ID, and authorization, Bearer followed by a Globus access token. The class AuthManager in web_service/utils.py checks them in this order:

    1. subject is a UUID.
    2. The token has the Bearer prefix, is 33 to 254 characters long, and holds only letters, digits and underscores.
    3. Globus token introspection, called with the service's confidential client (SERVER_CLIENT_ID and SERVER_SECRET), reports the token active.
    4. The token's sub is the subject header.
    5. The token's audience includes SERVER_CLIENT_ID.
    6. The token's scopes include https://auth.globus.org/scopes/<SERVER_CLIENT_ID>/action_all.

    A request missing one of the headers gets FastAPI's 422. A failed check ends the request: the user, key, namespace and topic routes answer 200 with {"status": "error", "reason": ...}, and the consumer routes answer 401. Step 3 fails this way only when Globus answers that the token is inactive. When the introspection call itself fails, for example because Globus rejects SERVER_CLIENT_ID and SERVER_SECRET, the Globus SDK raises an AuthAPIError that the service does not catch, and the route answers 500. After the checks, the service trusts subject as the caller's identity and names the caller's resources after it.

    Each user's resources¶

    A namespace is the prefix of the Kafka names of a user's topics and consumer groups. Each user gets one, the default namespace, when the service creates the user.

    Resource Name Created by Deleted by
    IAM user the subject, under the path /msk-users/ POST /api/v3/user, or POST /api/v3/key when the keys table holds no key that is still active in IAM DELETE /api/v3/user
    IAM managed policy, attached to the user the subject, under the path /msk-policy/ the same as the user DELETE /api/v3/user
    IAM access key chosen by IAM POST /api/v3/key POST /api/v3/key when the keys table holds no key that is still active in IAM, DELETE /api/v3/key, DELETE /api/v3/user
    Default namespace ns- and the last 12 characters of the subject without dashes the same as the user DELETE /api/v3/user
    Kafka topic <namespace>.<topic>, with 1 partition and replication factor 2 POST /api/v3/{namespace}/{topic} DELETE /api/v3/{namespace}/{topic}, DELETE /api/v3/user
    Kafka consumer group <namespace>.<group_name> the first consumer that joins it not deleted by the service

    The policy lets the IAM user connect to the cluster in MSK_CLUSTER_NAME, and use only the topics, consumer groups and transactional IDs whose names start with the user's default namespace and a dot. With the user's access key, a Kafka client can therefore produce to and consume from the user's topics directly, without the service, but its consumer group IDs and transactional IDs must have the same prefix, such as ns-0123456789ab.workers. The cluster refuses any other group or transactional ID with an authorization error, so no user can join, describe or commit offsets for another user's group, or fence another user's transactional producer. The consumer routes name their groups <namespace>.<group_name> and connect as the service, so this does not limit them. When IAM_USER_PERMISSIONS_BOUNDARY_ARN is set, the service also sets the policy it names as the user's permissions boundary.

    The service writes the policy when it creates the user, so a change to it reaches only the users created after the change. scripts/update_user_policies.py brings the other users' policies up to date (Update the users' IAM).

    POST /api/v3/key returns the key stored for the user, with fresh set to false, when the keys table holds one that is still active in IAM. It skips the check for a key under 5 minutes old, which IAM may not list yet, and returns the stored key when IAM does not answer. Otherwise it creates the user and the default namespace if they are missing, deletes every access key the IAM user holds, creates a new key, stores it, and returns it with fresh set to true. Both answers include endpoint, the value of DEFAULT_SERVERS.

    Namespace and topic names are 3 to 32 characters of letters, digits, dashes and underscores, and do not start or end with a dash or an underscore. A namespace is unique across all users. A namespace holds at most MAX_TOPICS_PER_NAMESPACE topics, 50 by default.

    The DynamoDB tables¶

    Three environment variables name the tables, and their defaults are the production tables. Every table has one string partition key. When a table does not exist, a write that adds an item, or adds to a set, creates it with on-demand billing; deletes from a missing table are ignored, and reads from it find nothing.

    Variable (default) Partition key Items
    KEYS_TABLE_NAME (diaspora-keys-table) subject One per user that holds a key: access_key, secret_key and create_date of the user's current IAM access key.
    USERS_TABLE_NAME (diaspora-users-table) subject One per user: namespaces, the set of namespaces the user owns. One more item, with the key __global_namespaces__, holds every namespace any user owns, which keeps namespace names unique.
    NAMESPACE_TABLE_NAME (diaspora-namespace-table) namespace One per namespace that has had a topic: topics, the set of the namespace's topic names, without the namespace prefix.

    Every read is strongly consistent, so a read sees every write made before it. Before a Kafka call, the service checks in these tables that the caller owns the namespace.

    State in memory¶

    ConsumerService keeps the consumer instances that the consumer routes create. The routes follow the consumer API of the Confluent REST Proxy v2. Each instance holds one KafkaConsumer, connected as the service, and the service finds it by the subject, the namespace, the group name and the instance ID. Only the subject that created an instance can use it. A background thread looks every 30 seconds for instances idle for longer than CONSUMER_INSTANCE_TIMEOUT_MS (5 minutes by default) and closes them. When the process stops, it closes them all at once, within 8 s in all. An instance created with auto.commit.enable set to true commits its positions before it closes, at a delete, at the reaper's close and at shutdown (Instance lifecycle). A subject may hold 4 instances and the service 12.

    These limits bound the memory of the consumer routes:

    • An idle instance holds what kafka-python fetched ahead for its next fetch: the next reply of each broker, however long the instance sits idle. A fetch asks each broker for at most 1 MiB, but a broker returns a first record batch larger than that whole, so an instance can hold 8 MiB per broker. Pausing the instance's partitions after each fetch does not drop it.
    • The service polls for 3 fetches at once. A fetch reads a record of up to 8 MiB from each broker, decodes it and encodes the reply. A reply holds at most 2 MiB of JSON, except a first record larger than that, which is returned alone and written in chunks of about 256 KiB, so its JSON (about 10.7 MiB for an 8 MiB record as base64, and up to 48 MiB as the JSON string of 8 MiB of control characters) is never held whole. Header values are written a piece at a time too.
    • A json instance checks that each key and value it returns is JSON, one check at a time in the whole service. Before it checks, it estimates the memory the check takes from the counts of the value's brackets, commas, quotes and colons, and returns a value whose estimate is over 32 MiB as text, without the check. In a test on macOS, the check of an 8 MiB array of empty arrays took 180 MiB, which the bound refuses.

    The service's worst case on a cluster of two brokers adds up as follows. The measured numbers come from tests on macOS against one local broker, except where the row says otherwise; the others are derived from the code.

    Part Memory Source
    The service at rest 99 MiB Measured
    Records fetched ahead by 12 instances, 8 MiB from each of 2 brokers 192 MiB Derived; one broker's 8 MiB per instance was measured
    12 instances' clients, TLS connections and heartbeat threads 54 MiB Measured against the cluster at 4.1 to 4.2 MiB each, rounded up to 4.5 MiB. This corrects the 1 MiB each measured against the local broker without TLS
    3 fetches, each with an 8 MiB record from each of 2 brokers 216 MiB Measured at 71 MiB for one fetch whose broker returned two 8 MiB records
    One check that a json instance's key or value is JSON 32 MiB Derived from the estimate's bound
    The produce routes: one parse of up to 192 MiB, 48 MiB of bodies and records, and the producer's copies of those records 288 MiB Derived
    Total 881 MiB

    That leaves about 143 MiB of the node's 1 GB. Creating and deleting 16 instances round after round, under the earlier cap of 16, in the service's image on a quarter of a CPU, raised the service's memory by 60 to 70 MiB, which that covers. In the local tests, with 12 idle instances holding 64 MiB of fetched-ahead records, 4 fetches of one 8 MiB record each raised the service from 99 MiB to 320 MiB as base64 and to 350 MiB as JSON of control characters.

    WebService and NamespaceService each hold a lock. The lock in WebService serializes user and key operations, including the Kafka topic deletes of DELETE /api/v3/user. The lock in NamespaceService serializes only the DynamoDB step of namespace and topic operations: the topic routes call Kafka outside any lock. Both are Python threading locks, so they serialize requests only within one process.

    Because of this state, the service runs one worker on one node (Lightsail scale 1). A second worker or node would not hold the consumer instances the first created, so requests for them would get 404 with error code 40403 (Consumer instance not found). Two processes could also run user, key or topic operations on the same records at the same time, since neither would hold the other's locks. Every restart or deploy drops the consumer instances, and clients must create new ones (One worker).
